## Context

The generator has one shape for every format:
1. A **reader** (`OpenApiReader`, `WsdlReader`) turns a source into an `ApiDefinition`, made of a root `Group` plus section `Group`s of `Operation`s, `Model`s and auth.
2. `PackageEmitter` writes it:
   - `DictClientEmitter` writes each level's `client.py`, whose routes return dicts;
   - with `--models`, `ModelPlacement`/`ModelModules`/`SchemaModuleEmitter` write pydantic models, one module per model or per cycle, placed in the level that uses them;
   - `ModelsClientEmitter` writes the `.models` view on `TypedClient`.
3. Regeneration deletes only files that start with the "Generated by apiroute" marker. Then ruff formats the output.

SOAP was added by giving `Operation` a `soap` field and teaching `DictClientEmitter` to emit `SoapBody`/`SoapDecoder` arguments. GraphQL fits the same seams. The runtime pieces already exist: `graphql_route` (variables bound by snake_case name, `data=` unwrapping, `GraphQLError`) and `graphql_schema_loader` (SDL/JSON loading that tolerates newer introspection).

Client repositories (see `.agent/skills/apiroute-client.md`) regenerate on a schedule and commit the result, so the output must be deterministic and diff cleanly. They commit a `specs/` snapshot, which for GraphQL means a schema file plus the hand-written operations.

## Goals / Non-Goals

**Goals:**
- Operations first: the user owns the `.graphql` files, and the generator never invents selections except `__typename` where it's needed to tell types apart.
- Fail before writing, with every problem across all files, located by file:line:column.
- The output looks like the other formats: the same dict and `.models` layers, lazy loading, the marker, ruff-clean code, and Python 3.10 compatibility.
- Deterministic output, so the same inputs give byte-identical files.

**Non-Goals:**
- Subscriptions; operations generated from the schema; fragment base classes (see Open Questions); persisted-query manifests; pagination helpers.
- Validating at run time in generated clients. The generator already validated, so generated clients don't set `graphql_schema` and don't need graphql-core at run time.

## Decisions

### 1. Inputs: a schema, plus a directory of operation files whose layout is the section layout

`apiroute generate graphql <schema> --operations <dir> -o <out>`:
- `<schema>` is loaded through the runtime loader (refactored to expose `load_schema_file(path)`), so SDL, `.json` and the tolerance for newer introspection behave the same as `graphql_schema`. An `http(s)://` value is introspected with httpx: a POST of graphql-core's `get_introspection_query()`, sent with any `--header` values.
- `<dir>` is read recursively. Files are `*.graphql` and `*.gql`, sorted by path for determinism.
  - Top-level files are root-client operations, and each first-level subdirectory is a section named after it (`repos/` → `client.repos`, class `ReposSection`).
  - Deeper directories belong to their first-level section. Section nesting stays one level deep, matching OpenAPI tags.
- Fragments are global across all files, as in graphql-codegen, because GraphQL fragment names are unique within one API.

*Alternative:* one file containing every operation. Rejected because a directory gives sections for free and keeps diffs local.

### 2. Validation before emission, with all errors accumulated

The reader:
1. parses every file, keeping its path, and collects all operations and fragments;
2. checks:
   - every operation is named;
   - operation and fragment names are unique (reporting both locations on a duplicate);
   - subscriptions are refused, with a message;
   - every fragment is used (unused ones are a warning).
3. For each operation, it builds its document (the operation plus the fragments it uses, transitively), validates it with `graphql.validate`, and maps graphql-core's locations back to the file the definition came from.

All problems are raised together as one `ValueError`, which the CLI prints. A use of a deprecated field or enum value prints a warning with its `deprecationReason`.

*Alternative:* stop at the first error. Rejected because a schema update that breaks five operations should be fixed in one pass.

### 3. The emitted document: `print_ast` of the operation and its fragments

Each method inlines its document as a triple-quoted string: the operation followed by its fragments in name order, printed by `graphql.print_ast`. Printing normalizes whitespace and drops comments, so cosmetic edits to a `.graphql` file don't churn the generated code and the output is deterministic. The original leading `#` comment block of an operation becomes the method's docstring.

Where a selection set on an interface or union contains type conditions (inline fragments, or spreads of fragments on concrete types), the generator adds `__typename` to it if it isn't there. This edits the AST before printing, so the emitted document shows exactly what's sent.

### 4. `ApiDefinition` additions: `GraphQLOperation` metadata and `"variable"` parameters

Following the `soap` precedent:
- `Operation.graphql: GraphQLOperationSpec | None`, holding `document`, `operation_name`, `operation_type` and `path` (the endpoint path, default `/graphql`).
- Variables become `Parameter(location="variable")`. `wire_name` is the variable name, and `name` is `safe_identifier(snake_case(variable))`. When that differs from the runtime's automatic snake_case match (for example `$from` → `from_`), the emitter passes `variables={"from": "from_"}`.
- `Operation.response` is the result model, and `response_plain` is `dict[str, Any]`.

`DictClientEmitter._route` gets a GraphQL branch that writes:
```python
@graphql_route(
    """query Repo($owner: String!, $name: String!) { repository(owner: $owner, name: $name) { ...RepoFields } }
fragment RepoFields on Repository { name stargazerCount }""",
    path="/graphql",
)
def repo(self, *, owner: str, name: str) -> dict[str, Any]:
    """The repository with its star count."""
```
- Variables are keyword-only, with required ones first.
- `operation_name=` is omitted because it's always the document's name.
- Mutations get no special flag, because the runtime already treats them as non-idempotent.

`ModelsClientEmitter` needs no GraphQL branch beyond the parameter list: `TypedClient._call` already turns input models into plain data and validates the result.

### 5. Result models follow the selection set, flattened

For each operation, the mapper walks the selection set alongside the schema types:
- **Naming:** the root is `<Operation>Result`. Each object-valued field gets a model named `<Parent><FieldPascal>` (`RepoResult.repository: RepoRepository`). An alias names the field and the model: `owner: author { ... }` gives the field `author`, typed `RepoRepositoryAuthor`. Names are made unique with the existing `unique()`.
- **Fields:** a field's wire name is its response key (the alias, if any). The Python name is `safe_identifier(snake_case(key))`, with `alias=` set when they differ.
- **Nullability:**
  - A non-null field is required.
  - A nullable field is `T | None`, still required, because GraphQL always returns selected fields.
  - A field under `@include`/`@skip`, or in a type-conditioned fragment on a concrete type that may not match, gets `= None`.
  - A list is `list[T]`, with item nullability kept.
- **Fragments are flattened:** their fields merge into the selecting model. When the same response key is selected twice, the sub-selections merge too, as GraphQL's field merging does.
- **Interfaces and unions:**
  - With no type conditions, the result is one model holding the shared fields.
  - With type conditions, the result is one model per possible concrete type (shared fields plus that type's conditional fields), each with `typename: Literal["User"] = Field(alias="__typename")`. The field's type is then their union, a `Model` alias, with a fallback model for possible types the operation didn't name, which carries only the shared fields and `typename: str`.
- **Scalars:** `Int`→`int`, `Float`→`float`, `String`/`ID`→`str`, `Boolean`→`bool`. Custom scalars become `Any`, unless `--scalar Name=module:attr` is given, in which case the models import that type and pydantic parses it (e.g. `datetime:datetime`).
- **Enums** become `Literal[...]` aliases. **Input objects** become pydantic models with snake_case fields and wire aliases. Optional input fields default to `None` and are left out when unset, because `TypedClient`'s plain conversion uses `exclude_unset`. Only the enums and inputs reachable from some operation are emitted.

Result models are placed in their operation's group, and shared enums and inputs in the root, using the existing `ModelPlacement`.

*Alternative:* fragments as base classes (ariadne-codegen). It lets functions accept "anything with `RepoFields`", but needs `Model.bases` support in the emitters and makes field merging harder. It's deferred (see Open Questions) and can be added later without breaking flattened output, since the field names stay the same.

### 6. Methods return the whole `data`, not a single root field

`client.repo(...)` returns `{"repository": {...}}` (or `RepoResult`), not the `repository` value. Unwrapping a lone root field automatically would change a method's return type, which is a breaking change in generated code, the moment someone adds a second root field to the operation. Users who want the inner value write `.repository`.

### 7. `--endpoint` and `fetch-schema`

- **`--endpoint`:** `--endpoint https://api.github.com/graphql` becomes `base_url = "https://api.github.com"` and `path="/graphql"` on each route. Without it, `base_url` stays unset (the client is then constructed with `base_url=`) and the path defaults to `/graphql`. `--base-url` isn't accepted for this format, to avoid two ways to say the same thing.
- **`fetch-schema`:** `apiroute fetch-schema <endpoint> -o <file> [--header "Authorization: Bearer $TOKEN"]` writes `print_schema` SDL, or the raw introspection JSON when `<file>` ends in `.json`. SDL is the default because it reads and diffs well in a client repository's `specs/`. Header values are taken as given, so tokens come from the shell's environment, never from a file apiroute writes.

### 8. Package source line and determinism

The marker line names both inputs: `Generated by apiroute <v> from <schema> and <operations-dir>`. Operations, fragments, models and fields are emitted in a fixed order (by file path, then by position in the file, for operations; by name for shared models). A test generates the package twice and compares the files byte for byte.

### 9. Shared generator fixes found along the way

Two changes touch code that every format uses. Neither changes today's OpenAPI or WSDL output; the fixtures generate byte-identical packages before and after:
- **The header.** It's built in one place (`codegen/generated_header.py`). "Do not edit" moves to a second line only when one line would pass 100 characters, which a GraphQL source (two names) can.
- **Soft keywords.** `safe_identifier` used to ask the running Python, and `type` is a soft keyword only from 3.12, so a parameter named `type` was `type_` or `type` depending on the Python that generated it. The list is now fixed at 3.12's (`_`, `case`, `match`, `type`), matching what current Pythons already produced.

Union results are plain unions (`A | B | Other`): pydantic's smart mode picks the member whose `__typename` Literal matches, and `Field(union_mode=...)` isn't available in pydantic 2.0, the oldest the extras allow.

### 10. What testing against GitHub's real API changed

The fixture schema is small. Running the generator against GitHub's published schema (1.5 MB of SDL), generating from a live `fetch-schema` of `api.github.com/graphql` (SDL and JSON), and making read-only calls with the generated client turned up two things:
- **Server schemas are loaded with `assume_valid=True`.** GitHub's schema deprecates implementation fields whose interface fields aren't deprecated, which graphql-core 3.3 rejects as an invalid schema, stopping every validation. A client describes what a server answers; it shouldn't re-validate the server. This also fixes runtime `graphql_schema` validation (1.8.0) with GitHub's schema.
- **`GraphQLError.codes` falls back to a top-level `type`.** GitHub sends `"type": "NOT_FOUND"` rather than `extensions.code`.

## Risks / Trade-offs

- **[Generated model names get long]** (`ViewerResultViewerRepositoriesNodesOwner`) → They're predictable, and aliases let users shorten paths. Fragment base classes, if added later, would help.
- **[Adding `__typename` surprises users reading the generated document]** → It only happens where type conditions require it, and it's visible in the emitted document. This is documented.
- **[Introspection over HTTP in `generate`]** needs credentials and network → It's optional. Client repositories use `fetch-schema` into `specs/` and generate from the file, so builds are reproducible.
- **[Validation on graphql-core 3.2 vs 3.3 can differ in messages]** → Tests assert on locations and key phrases, not exact wording, and the lowest-dependencies CI job covers 3.2.
- **[A custom scalar mapped with `--scalar` might not be pydantic-parsable]** → It's the user's choice. The default `Any` is always safe.

## Migration Plan

This is a new format and a new command. OpenAPI and WSDL output is unchanged; existing tests and a generated-package comparison guard that. Release as `feat:`. A follow-up updates the client-repository skill, which is part of this change's tasks, so client repositories can add GraphQL APIs.

## Open Questions

- **Fragment base classes:** should named fragments become model base classes, as ariadne-codegen does? This is deferred until a client repository needs functions typed by fragment.
- **Custom scalars:** should `--scalar` also accept a serializer for variables (e.g. `datetime` → ISO string)? pydantic's JSON mode already handles common types, so this waits for a concrete case.
